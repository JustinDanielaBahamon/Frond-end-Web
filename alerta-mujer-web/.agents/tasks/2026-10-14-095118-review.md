# Device Status Screen Implementation

Implementation of a comprehensive device diagnostics dashboard for the Alerta Mujer web application. The module provides system administrators and users with visibility into browser permissions, service availability, device information, and critical app features. The component uses Angular signals for reactive state management and integrates with two custom services (DeviceInfoService and PermissionsService) to gather environmental data.

**Watch for:** Activity log cross-user leak potential (confirmed), missing accessibility attributes on interactive cards (confirmed), CSS variable duplication instead of token reuse (confirmed), inconsistent localStorage key naming (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The component correctly scopes activity logs by user ID to prevent cross-user leaks when users share devices, storing logs under `device-activity-log-user-${userId}` keys. However, critical feature data (emergency contacts, location, notification token) uses shared localStorage keys that lack user scoping, creating a potential cross-user information leak.

The permission checking system has a fallback-first design: when the Permissions API is unavailable (Safari, older browsers), it returns 'unavailable' rather than attempting direct API checks, which means users see "unavailable" even when functionality works. The system notifies users of this with an info banner.

Four interactive test buttons (geolocation, notification request, notification display, connectivity) provide hands-on diagnostics, with results logged to the activity feed. The connectivity test attempts the backend health endpoint first, then falls back to an external canary to distinguish between backend downtime and network failure.

The UI uses a collapsible grid layout with 2-column responsive sections for services/device info and activity/tests. CSS variables are locally defined in `:host` rather than imported from the project-wide token system at `src/app/shared/styles/tokens.scss`.

Interactive cards in the "Critical Features" section lack ARIA attributes, making them inaccessible to screen readers despite conveying important status information.

<details>
<summary>Issues (7)</summary>

1. **Critical feature localStorage keys not user-scoped** — `last_location`, `notification_token`, and `emergency_contacts` lack user ID prefixes. On shared devices, user B sees user A's data. Scope these keys by user ID like the activity log already does.

2. **Cache clear logs user out** — The clearCache method preserves `auth_token`, `user_data`, and `emergency_contacts`, but AuthService actually stores the session under `alerta_session`. This key will be deleted, logging the user out. Preserve `alerta_session` instead of `auth_token`.

3. **Missing ARIA attributes on status cards** — The "Critical Features" cards (session, location, token, contacts) lack `role`, `aria-label`, and `aria-live` attributes. Screen readers cannot convey status changes. Add semantic roles and labels.

4. **CSS variable duplication** — Device.scss duplicates variables already defined in `tokens.scss` (--color-principal, --font-size-xs, etc.). Import and reuse the project tokens instead of redefining them locally.

5. **Permission unavailable vs. functionality broken** — When Permissions API is unavailable, the system shows "unavailable" even if functionality works (e.g., Safari supports geolocation but not the query API). Consider attempting a test call for critical permissions like geolocation when the query returns unavailable.

6. **Inconsistent localStorage key naming** — Most keys use snake_case (`last_location`, `auth_token`) but activity log uses kebab-case (`device-activity-log-user-${userId}`). Standardize on snake_case.

7. **Connectivity test hardcoded localhost fallback** — The backend URL falls back to `http://localhost:8080` when `window.__env?.apiUrl` is undefined. This will always fail in production. Use Angular's `environment.apiUrl` instead.

8. **Export diagnostic includes potentially sensitive data** — The diagnostic export includes full userAgent, screen resolution, and activity logs. Consider warning users that the export may contain identifying information before download.

## Activity log scoped correctly, critical features not

The activity log uses user-scoped keys to prevent cross-user leaks:

```typescript
private addActivityLog(type: ActivityLog['type'], message: string): void {
  const userId = this.currentUserId;
  if (!userId) {
    console.warn('Cannot log activity: no user session');
    return;
  }
  // ...
  const logKey = `device-activity-log-user-${userId}`;
  localStorage.setItem(logKey, JSON.stringify(newLogs));
}
```

This prevents user B from seeing user A's diagnostic history on shared devices. However, the critical features check reads from shared keys:

```typescript
const lastLocation = localStorage.getItem('last_location');
const notificationToken = localStorage.getItem('notification_token');
const emergencyContacts = localStorage.getItem('emergency_contacts');
```

On a shared kiosk or family computer, user B logs in and sees user A's emergency contacts count, last captured location timestamp, and notification token status. These should use `${key}-user-${userId}` naming like the activity log. The impact depends on where these keys are written—if the app only writes them with user scoping, this is a display bug; if they're written without scoping, it's a data leak.

## Cache clear logs user out

The clearCache method protects `['auth_token', 'user_data', 'emergency_contacts']`, but AuthService (line 173-182) actually stores the session under `alerta_session`. This key will be deleted, logging the user out. The whitelist should check for `alerta_session` instead of `auth_token`.

## Permissions API fallback behavior

The PermissionsService returns `'unavailable'` when `navigator.permissions` is missing or a query fails:

```typescript
if (!('permissions' in navigator)) {
  return of({ 
    name, 
    state: 'unavailable', 
    canRequest: false 
  });
}

return from(navigator.permissions.query({ name: queryName as any })).pipe(
  map(result => ({...})),
  catchError(() => of({ 
    name, 
    state: 'unavailable' as const, 
    canRequest: false 
  }))
);
```

Safari doesn't support the Permissions API but supports most of the underlying functionality (geolocation, notifications). This means Safari users see "Ubicación: No disponible" even though geolocation works fine. Consider adding a test call for critical permissions (geolocation, notifications) when the query returns unavailable, to differentiate "query unsupported" from "feature unsupported."

## Missing ARIA attributes on status cards

The "Critical Features" section displays session, location, token, and contact status as visual cards:

```html
<div class="device-feature-item">
  <div class="device-feature-item__icon" [ngClass]="features.sessionActive ? 'device-feature-item__icon--exito' : 'device-feature-item__icon--peligro'">
    <i class="ti ti-login"></i>
  </div>
  <div class="device-feature-item__body">
    <span class="device-feature-item__label">Sesión</span>
    <span class="device-feature-item__value">{{ features.sessionActive ? 'Activa' : 'Inactiva' }}</span>
  </div>
</div>
```

These cards convey critical status but lack semantic roles. Screen readers will read the text but won't indicate that this is a status indicator. Add `role="status"`, `aria-label="Estado de sesión"`, and `aria-live="polite"` to make state changes accessible. The same issue applies to the permission items in the "Permisos del Navegador" grid.

## CSS variable duplication vs. token reuse

Device.scss defines its own variables:

```scss
:host {
  --color-principal: #6d28d9;
  --color-principal-claro: #7c3aed;
  --color-acento: #0891b2;
  --font-size-xs: 0.75rem;
  --font-size-sm: 0.875rem;
  // ...
}
```

These duplicate the project-wide tokens defined in `src/app/shared/styles/tokens.scss` (lines 48-56, confirmed by grep). The comment at the top of device.scss says "Reutilizamos la misma paleta de home para consistencia visual," but redefining rather than importing breaks the single source of truth. If the design system changes `--color-principal` from `#6d28d9` to `#7c3aed` globally, device.scss won't pick it up.

Home.scss has the same issue (lines 7-8 of home.scss). Both modules should import `tokens.scss` or consume variables from a shared parent (:host-context, or a scoped wrapper). The dark theme override at `dashboard-dark.scss` line 149 already overrides `--color-principal` at the `app-dashboard` scope, so the local `:host` definition may be fighting with the theme system.

## localStorage key naming inconsistency

The activity log uses kebab-case (`device-activity-log-user-${userId}`) while the rest of the app uses snake_case (`last_location`, `alerta_session`, `emergency_contacts`). Standardize on snake_case: `device_activity_log_user_${userId}`.

## Connectivity test hardcoded localhost fallback

The backend URL is derived from `window.__env?.apiUrl || 'http://localhost:8080'`. If `__env` is not set in production, this will test against localhost, which will always fail in deployed environments. The component should use Angular's `environment.apiUrl` instead, or at minimum log a warning when falling back to localhost.



## Export diagnostic data exposure

The exportDiagnostic method includes:

```typescript
const diagnostic = {
  timestamp: new Date().toISOString(),
  deviceInfo: this.deviceInfo(),  // includes full userAgent, screen resolution
  permissions: this.permissions(),
  services: this.services(),
  criticalFeatures: this.criticalFeatures(),  // includes token status, location timestamp
  activityLog: this.activityLog(),  // includes user actions
  screenInfo: this.deviceInfoService.getScreenInfo()  // includes DPR
};
```

The full userAgent and screen resolution can fingerprint a device. Activity logs may contain sensitive diagnostic messages. Consider adding a confirmation dialog warning users that the export contains potentially identifying information, especially if they plan to share it with support.

## Not tested

- Multi-user scenario: clearing cache with user A logged in, then switching to user B
- Permission state updates: if a user denies a permission in browser settings, does the UI reflect it on next refresh?
- Notification constructor throwing in environments where it's unsupported (wrapped in try-catch, good)
- Geolocation timeout and error code handling (implemented, not tested)
- Fallback connectivity test when backend health endpoint returns 500 vs. network error (both branches exist, not exercised)
