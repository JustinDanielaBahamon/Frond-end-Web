# Dashboard security status integration with backend

The home dashboard component now fetches real security status from a new `UserSecurityStatusService` that checks emergency contacts, browser permissions, and activation methods. The service determines whether the user's configuration is complete (verde), needs attention (amarillo), or is critically incomplete (rojo). The template displays exactly 4 security items (contacts, activation, location, notifications) with dynamic color indicators, and "Evidencias almacenadas" has been removed.

**Watch for:**
- **Private field access via bracket notation** (likely) — `authService['_currentUser$']` bypasses TypeScript visibility, fragile if AuthService refactors
- **Hardcoded activation method stub** (confirmed) — `checkActivationMethod()` returns `'Movimiento'` for every user; all users appear to have activation configured when they may not
- **Missing subscription cleanup** (confirmed) — `cargarEstadoSeguridad()` in `ngOnInit` subscribes but never unsubscribes; memory leak on navigation
- **Hardcoded userId in zone fetch** (confirmed) — map zones use `getByUser(1)` instead of the current user's ID

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The security status service correctly fetches contacts via `EmergencyContactService.getByUsuario()` and checks browser permissions for geolocation and notifications, returning 4 requisitos that map to dashboard items. The color logic implements the requested rule: RED if fewer than 2 contacts OR at least 2 missing items; YELLOW if exactly 1 missing; GREEN if all 4 are OK. The template conditionally applies CSS classes to the check icons (exito, advertencia, peligro) based on `estadoGeneral.color`, and the panel header shows a pulsing dot indicator. The service accesses `authService['_currentUser$'].value` via bracket notation to bypass private visibility, which works but breaks encapsulation. The activation method check is stubbed to always return `'Movimiento'`, making every user appear to have an activation method when the backend endpoint doesn't exist yet. The subscription in `cargarEstadoSeguridad()` is never cleaned up, leaking memory on navigation away from the dashboard.

2. **Activation method stub** — `checkActivationMethod()` always returns `'Movimiento'`. Until the backend endpoint exists, return `null` and mark as not configured, or document that this is a temporary optimistic default and must be replaced.

4. **Hardcoded userId in zones** — `cargarZonasPeligrosas()` calls `getByUser(1)` instead of the authenticated user's ID. Use the same user object from AuthService.

<summary>Details</summary>

## Color logic: verde, amarillo, rojo

The logic counts how many items are not `cumplido` (failedCount). If `cantidadContactos < 2` OR `failedCount >= 2`, the status is `critico` / `rojo`. If `failedCount === 1`, status is `advertencia` / `amarillo`. Otherwise, `seguro` / `verde`. The contact check is duplicated in the condition (contacts < 2 OR failedCount >= 2), which means if contacts < 2, the status is RED even if only 1 total item is missing. This is correct per the requirement ("si solo tiene 1 contacto en estado rojo").

## Private field access via bracket notation

`const user = this.authService['_currentUser$'].value;` accesses a private `BehaviorSubject` by bypassing TypeScript visibility. This works at runtime but breaks encapsulation. If AuthService renames or refactors `_currentUser$`, this line breaks silently. AuthService already exposes `currentUser$: Observable<User | null>`, but the service needs the synchronous `.value`. The correct fix is to add a public getter in AuthService (`getCurrentUser(): User | null { return this._currentUser$.value; }`).

## Activation method stub always returns 'Movimiento'

```typescript
private checkActivationMethod(): Observable<string | null> {
  // TODO: Replace with actual backend call
  return of('Movimiento');
}
```

This makes every user appear to have an activation method configured. The comment acknowledges this is temporary, but the behavior is misleading: users without an activation method will see "Método de activación: Movimiento" with a green check. This fails the honesty requirement. Return `null` until the backend endpoint exists, or document prominently that this is an optimistic default and must be replaced before production.

## Memory leak: subscription never cleaned up

`cargarEstadoSeguridad()` calls `this.securityStatusService.getSecurityStatus().subscribe(...)` in `ngOnInit`. The subscription is never stored or unsubscribed. When the user navigates away from the dashboard, the subscription remains active, leaking memory. The correct fix is to use `takeUntilDestroyed()` in the pipe (requires Angular 16+, already used elsewhere in the codebase based on imports), or store the subscription and unsubscribe in `ngOnDestroy()`.

## Hardcoded userId in zone fetch

`cargarZonasPeligrosas()` calls `this.zoneService.getByUser(1)`, hardcoding userId 1. This fetches zones for a different user if the current user has a different ID. The correct fix is to use `user.id` from the AuthService, the same way the security status service does.

## Error handling: fail-closed on backend errors

The service's `forkJoin` wraps contact fetch in `catchError(() => of(0))`, treating backend failures as 0 contacts and triggering RED status. Geolocation and notification checks wrap their promises in `.catch(() => false)`, treating permission errors as "not granted". The component's subscribe error handler sets a fallback 4-item array with all items unconfigured. If the backend is down, the dashboard shows RED status with 0% configured, which is safer than showing green.
