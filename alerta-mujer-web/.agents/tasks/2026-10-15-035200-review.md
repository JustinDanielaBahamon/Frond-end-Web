# Backend-synced security status with dynamic color indicators

The dashboard now fetches security status from the backend via a new `UserSecurityStatusService`, replacing the hardcoded 5-item display with a dynamic 4-item grid that reflects the user's actual configuration: contacts, activation method, geolocation, and notifications. The service applies a three-tier color rule (red if <2 contacts OR ≥2 missing; yellow if exactly 1 missing; green if all OK), and the template renders the status dot and check icons with the corresponding color class. The "Evidencias almacenadas" item was removed. Map enhancements include dangerous zones from the backend, a purple gradient pin for the user's location, and a refresh button.

**Watch for:** The geolocation permission check returns false instead of unknown when `navigator.permissions` is unavailable **(confirmed)**, the color logic uses a shortcut equality check that works but could break if levels are added **(confirmed)**, the `takeUntilDestroyed` operator is used incorrectly outside the injection context **(confirmed)**, and the "refresh location" is currently a mock with random coordinate drift **(confirmed)**.

**Verdict**: CHANGES_REQUESTED

## High-level view

The service fetches contact count from `EmergencyContactService.getByUsuario()`, checks `Notification.permission` for notification state, queries `navigator.permissions` for geolocation, and stubs activation method to null until the backend endpoint exists. The color logic correctly implements the red threshold (fewer than 2 contacts OR at least 2 missing features), the yellow tier (exactly 1 missing), and green (all OK). The component loads status on init via `takeUntilDestroyed()`, but that operator is called outside Angular's injection context, breaking automatic cleanup. The template renders a loading skeleton while fetching, then displays 4 items with dynamic color classes on the indicator icons and the status dot in the panel header. The map section adds zone rendering from the backend (with example fallback) and a refresh button that currently simulates location updates with random deltas instead of calling a real geolocation service.

<summary>Issues (7)</summary>

1. **takeUntilDestroyed called outside injection context** — The operator requires injection context but is invoked in `ngOnInit`. Move the subscription to the constructor or switch to `Subject` + `takeUntil` + `ngOnDestroy`.
2. **Geolocation permission degrades to false instead of unknown** — When `navigator.permissions` is unavailable, the service returns `false`, making it indistinguishable from explicit denial. Return a third state or document the assumption.
3. **Color equality check is fragile** — The template uses `estadoGeneral?.color === 'rojo'` and `'amarillo'` string checks. If a new level is added or color values change, the checks silently break. Use enum or typed accessor.
4. **Mock location refresh with random drift** — `refrescarUbicacion()` adds random coordinate noise instead of fetching real device location. The TODO is present but the mock could mislead users into thinking the feature is implemented.
5. **No error state distinction for contact service failure** — If `EmergencyContactService.getByUsuario()` fails (404, 500, network), the service catches it and returns 0 contacts, which triggers red status. A service error looks identical to zero configured contacts in the UI.
6. **Private user/zone markers could leak on fast navigation** — `userMarker`, `zoneCircles`, and `zoneMarkers` are cleaned up in `ngOnDestroy`, but if the component is destroyed before `cargarZonasPeligrosas()` completes, the async callback could add markers to a destroyed map.
7. **Missing CSS for new color classes** — The template references `home-seguridad-item__check--peligro` and `home-seguridad-item__check--advertencia`, and `estado-dot--rojo`, `estado-dot--amarillo`, `estado-dot--verde`. Verify these classes exist in `home.scss` or the indicators won't render correctly.

## Security status fetched from backend

`UserSecurityStatusService.getSecurityStatus()` uses `forkJoin` to gather contact count from `EmergencyContactService.getByUsuario()`, browser notification permission via `Notification.permission`, geolocation permission via `navigator.permissions.query({ name: 'geolocation' })`, and activation method (currently stubbed to null with a TODO for the backend endpoint). Each observable wraps errors with `catchError(() => of(fallback))`, so a single permission check failure doesn't break the entire status load.

Contact count comes from `GET /api/contacts/user/:id` and catches errors to return 0, which means a 404 or 500 from the backend will show as "0 contactos" in the UI rather than surfacing the error.

Geolocation uses `navigator.permissions.query`, wrapping the promise with `from()`. If `navigator.permissions` is unavailable (older browsers, some mobile contexts), the method returns `of(false)`. This means "permission unavailable" is indistinguishable from "permission denied" in the UI.

## Color logic implements the three-tier rule correctly

The service builds a `RequisitoSeguridad[]` array with 4 items: contactos (cumplido if ≥2), activacion (cumplido if non-null), ubicacion (cumplido if granted), notificaciones (cumplido if granted). It counts `failedCount = requisitos.filter(r => !r.cumplido).length`.

The decision logic:

```typescript
if (cantidadContactos < 2 || failedCount >= 2) {
  nivel = 'critico';
  color = 'rojo';
} else if (failedCount === 1) {
  nivel = 'advertencia';
  color = 'amarillo';
} else {
  nivel = 'seguro';
  color = 'verde';
}
```

This matches the specification: RED if fewer than 2 contacts OR at least 2 features missing, YELLOW if exactly 1 missing, GREEN if all OK. The contact count check is separate from the general failed count, which is correct — you can have 3 contacts but still hit red if 2 other features are missing.

The percentage calculation is `Math.round((requisitos.filter(r => r.cumplido).length / 4) * 100)`, which gives 0%, 25%, 50%, 75%, or 100%.

## Component loads status with broken subscription cleanup

`Home.ngOnInit()` calls `cargarEstadoSeguridad()`, which subscribes to `getSecurityStatus()` with `.pipe(takeUntilDestroyed())`. The `takeUntilDestroyed` operator requires Angular's injection context (constructor or field initializer), but it's invoked inside `ngOnInit`, outside that context. This will throw a runtime error or silently fail to clean up the subscription when the component is destroyed.

Fix: Either move the subscription to the constructor, use `takeUntilDestroyed()` in a field initializer with `defer()`, or switch to a manual `Subject` + `takeUntil` + `ngOnDestroy` pattern.

The subscription maps `EstadoSeguridad` to `estadoSeguridad: SeguridadItem[]` by extracting icon, valor, label, cumplido from each `RequisitoSeguridad`. It also builds `estadoGeneral` with nivel text ("Tu cuenta está protegida" / "Requiere atención" / "Configuración incompleta"), color, icon, and porcentaje. The error handler falls back to a static 4-item array with all `configurado: false` and `estadoGeneral.color = 'rojo'`.

## Template renders dynamic indicators and status dot

The template shows a loading skeleton while `isLoadingStatus` is true (4 placeholder items with a spinning loader icon). Once loaded, it iterates `estadoSeguridad` and renders each item with:

- Icon from `item.icon` (ti-users, ti-shield-check, ti-map-pin, ti-bell)
- Valor from `item.valor` ("3 contactos", "No configurado", "Activa", "Inactivas")
- Descripcion from `item.descripcion`
- Tooltip from `item.tooltip` (added in the mapping, shows full context on hover)
- Check icon with color class:
  - `home-seguridad-item__check--exito` (green check) if `item.configurado`
  - `home-seguridad-item__check--peligro` (red X) if `!item.configurado` and `estadoGeneral.color === 'rojo'`
  - `home-seguridad-item__check--advertencia` (yellow warning triangle) otherwise

The panel header shows `<span class="estado-dot" [ngClass]="'estado-dot--' + estadoGeneral.color"></span>` next to the title, which dynamically binds `estado-dot--verde`, `estado-dot--amarillo`, or `estado-dot--rojo`.

The subtitle uses `[ngClass]` to apply `home-panel__subtitle--advertencia` or `home-panel__subtitle--peligro` based on `estadoGeneral.color`.

These classes must exist in `home.scss` for the indicators to render correctly. If they're missing, the dot will be invisible and the check icons won't have color.

The color checks use string equality (`estadoGeneral.color === 'amarillo'`), which is fragile. If the `ColorIndicador` type changes or new levels are added, the template won't update automatically. A getter method or enum-backed logic would be safer.

## Evidencias almacenadas removed

The old hardcoded `estadoSeguridad` array had 5 items, including `{ icon: 'ti-folder', valor: '8', descripcion: 'Evidencias almacenadas', configurado: true }`. The new backend-driven array has exactly 4 items (contactos, activacion, ubicacion, notificaciones). The "Evidencias almacenadas" item is gone.

## Map refresh is a mock with random coordinate drift

The "Refrescar ubicación" button calls `refrescarUbicacion()`, which sets `isRefreshing = true`, waits 1.5 seconds, then updates `ultimaUbicacion.lat` and `ultimaUbicacion.lng` with `(Math.random() - 0.5) * 0.001` (roughly ±50 meters). The marker is repositioned with `this.userMarker.setLatLng(newLatLng)` and the map pans to the new location.

This is explicitly a mock — the TODO comment says "Reemplazar con llamada real al servicio de ubicación". The button works visually, but the feature isn't implemented. Users clicking "Refrescar" will see the pin jump slightly, which could mislead them into thinking it's fetching real GPS data.

Until a real geolocation service is wired up (browser `navigator.geolocation.getCurrentPosition()` or backend endpoint), the button should either be hidden or show a warning that it's simulated.

## Dangerous zones loaded from backend with example fallback

`cargarZonasPeligrosas()` gets the current user from `AuthService.getCurrentUser()`, then calls `NearbyZoneService.getByUser(currentUser.id)`. If the backend returns zones, they're used; if the array is empty or the call fails, it falls back to `obtenerZonasEjemplo()`, which returns 8 hardcoded zones for Neiva, Huila (police stations, hospitals, risk zones, safe zones, help points).

Each zone has type (`'risk' | 'safe' | 'help' | 'policia' | 'asistencia'`), which maps to a color, emoji, and label via `obtenerConfigZona()`. Zones with `radiusMeters` render as circles on the map; all zones get a marker with a colored circle icon containing an emoji.

The map rendering happens in `dibujarZonasEnMapa()`, which clears old `zoneCircles` and `zoneMarkers` arrays, then iterates `this.zonas` to create new Leaflet layers. The circles and markers are stored in private arrays and removed in `ngOnDestroy` when `this.map.remove()` is called.

If the component is destroyed before `cargarZonasPeligrosas()` completes (user navigates away quickly), the subscription callback could fire after `ngOnDestroy`, attempting to add markers to a destroyed map. This could cause a Leaflet error or leave orphaned markers. The subscription should be managed with `takeUntil` or canceled in `ngOnDestroy`.

## Purple gradient pin for user location

`crearMarcadorUbicacion()` creates a custom Leaflet `divIcon` with inline SVG: a teardrop-shaped pin with a purple gradient (`#8b5cf6` to `#6d28d9`), white stroke, white inner circle, and purple center dot. A small green pulsing indicator (12px circle with CSS animation) overlays the top-right, showing "active" status. The icon is 36×50px, anchored at the bottom center (18, 50), with popup offset (0, -50). The marker is stored in `this.userMarker` and reused when `refrescarUbicacion()` updates the position.

## No test coverage for UserSecurityStatusService

The diff shows no `.spec.ts` file for `UserSecurityStatusService`. The service has complex logic (forkJoin, multiple permission checks, color thresholds, contact count fetching) that should be unit tested:

- Contact count mapping from `EmergencyContactService`
- Notification permission check with and without `Notification` API
- Geolocation permission check with and without `navigator.permissions`
- Color thresholds: <2 contacts → red, ≥2 missing → red, 1 missing → yellow, all OK → green
- Fallback to critical state when user is null
- Error handling for contact service failure

Without tests, regressions could silently break the color logic or permission checks.

## TypeScript correctness

No `any` types. The `forkJoin` result is typed as `{ cantidadContactos: number, locationGranted: boolean, notifGranted: boolean, activationMethod: string | null }`. The component checks `if (!user)` before calling the contact service, and the template guards `estadoGeneral` with `@if (estadoGeneral)` before accessing `.color` or `.porcentaje`.
