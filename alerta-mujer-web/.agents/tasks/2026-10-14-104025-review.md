# Device Status Screen Implementation

The device status screen was added to provide comprehensive diagnostics for the Alerta Mujer web application, showing browser permissions, system capabilities, service status, and critical feature health. The component follows Angular standalone patterns, uses reactive signals, and integrates with existing services. The implementation includes permission checking, connectivity testing, activity logging, and diagnostic export capabilities.

**Watch for:** User-scoped localStorage keys prevent session leaks (**confirmed**). Notification constructor wrapped in try-catch for unsupported browsers (**confirmed**). API URL configuration needs runtime environment variable support (**likely**). Missing navigation menu integration (**confirmed**). Incomplete permission request flows for camera/microphone (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The component provides eight functional sections organized in a responsive two-column layout: browser permissions, service status, device information, critical features, activity log, functionality tests, and quick actions. Permission checking uses the Permissions API with fallbacks for unsupported browsers, explicitly noting that "unavailable" doesn't mean the feature won't work. Activity logs and critical feature data are scoped per-user using `user_${userId}` keys in localStorage to prevent cross-session leaks. The cache clearing function preserves `alerta_session` and user-scoped keys while removing temporary data. Connectivity tests use the backend health endpoint with a fallback to an external canary. The diagnostic export warns users about potentially identifying information before generating a JSON file. The component isn't integrated into the dashboard navigation menu despite being routed at `/dashboard/device`.

## User-scoped localStorage prevents cross-session leaks

Activity logs, emergency contacts, notification tokens, and last location are stored with keys scoped by user ID: `device_activity_log_user_${userId}`, `emergency_contacts_user_${userId}`, `notification_token_user_${userId}`, `last_location_user_${userId}`. This prevents User A from seeing User B's data after logout/login on a shared device. The component retrieves `currentUserId` from `authService.currentUser$` and refuses to log activity or load critical features if `userId` is null.

The cache clearing function explicitly protects user-scoped keys and `alerta_session`. However, it will clear any localStorage key that doesn't match the protected patterns, which could break third-party integrations or analytics if they store data in localStorage.

## Permission status messaging accounts for API limitations

The permissions panel displays a prominent note:

> Nota: Si un permiso muestra "No disponible", puede significar que tu navegador no soporta la API de consulta de permisos, pero la funcionalidad puede seguir funcionando mediante solicitudes directas.

This addresses a common UX issue: Safari and Firefox don't support `navigator.permissions.query()` for most permissions, returning "unavailable" even when the underlying feature works. The note sets correct expectations. The `PermissionsService` returns `{ state: 'unavailable', canRequest: false }` when the query API is missing, and the template maps this to a neutral badge.

Geolocation and notifications have explicit request buttons (`requestGeolocation()`, `requestNotificationPermission()`), but camera and microphone permissions show status without a way to request them. Either the request UI should be added, or these permissions should be removed from the display if they're not used by the app.

## Connectivity test uses backend health check with fallback

The `testConnectivity()` function first attempts to reach the backend health endpoint, falling back to an external canary (`google.com/favicon.ico`) if the backend is unreachable. This provides useful diagnostics: "Backend OK", "Backend unreachable but internet active", or "Total connectivity failure". However, `getApiUrl()` attempts to read `window.__env.apiUrl` at runtime, but there's no mechanism in the project to populate `__env`. The fallback uses `environment.apiUrl` which is replaced at build time, not runtime. If the intent is to support runtime configuration (e.g., for Docker deployments), a config loader is needed.

## Notification constructor wrapped for unsupported environments

The `testNotificationDisplay()` function wraps the `new Notification()` call in try-catch, preventing uncaught exceptions in environments where the Notifications API is present but the constructor is blocked (e.g., iOS Safari in private mode, or browsers that require service worker registration).

## Diagnostic export warns about identifying information

Before exporting the diagnostic JSON, the component shows a confirmation dialog warning about device identification data (browser, OS, screen resolution, activity history). However, the exported JSON includes the full user agent string, which can fingerprint a specific browser configuration. Consider either stripping the user agent or making the warning more specific about it.

## Activity log initialization races with user session load

The component calls `loadActivityLog()` in `ngOnInit()` immediately, but the `currentUserId` is set asynchronously via `authService.currentUser$.subscribe()`. On first render, `currentUserId` is null, causing a console warning "Cannot log activity: no user session" on every component mount. Defer the load until the subscription provides a user ID.



## SCSS uses project tokens inconsistently

The stylesheet imports `tokens.scss` but hard-codes some color values (`--color-acento: #0891b2`, `--color-neutral: #6b7280`, button color `#380759`) instead of mapping from tokens. The `tokens.scss` file defines `--purple-deep: #5b21b6`, which is close but not identical to `#380759`. All colors should come from the token system for visual consistency.



## Responsive design adapts to mobile

The dashboard bottom navigation includes links to Inicio, Alertas, and Ubicación, but not to Device. If the device screen is meant to be accessible on mobile, it should either be added to the bottom nav or linked from the settings screen.

## Component is routed but not linked in navigation

The `app.routes.ts` file includes the device route, but `DashboardLayoutComponent.links` does not include a Device entry. Users can access `/dashboard/device` by typing the URL, but there's no UI affordance to discover it. Add an entry to the sidebar with an appropriate icon (`fa-solid fa-microchip` or `fa-solid fa-laptop-medical`).
